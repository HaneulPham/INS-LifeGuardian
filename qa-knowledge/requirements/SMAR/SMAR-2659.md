## Requirement Summary

Correct CP Desktop Service Request checklist asset generation so the SafetyWatch stock type creates a SafetyWatch 3 asset with an `SF3` barcode and the SmartTracker stock type creates a SmartTracker 3 asset with an `ST3` barcode. The mapping applies when Generate Asset is executed from supported New Install and Repair Devices workflows. It must not migrate existing legacy assets or remove the ability to create legacy versions manually from Asset Management.

## Confirmed Scope

- CP Desktop Service Requests using New Install and Repair Devices.
- Process tab Generate Asset for SafetyWatch and SmartTracker stock types.
- Persisted Asset Type, environment Asset Type ID, barcode prefix, checklist completion, linked-device relationship, reopen persistence, and duplicate prevention.
- Existing and historical legacy Service Request assets.
- Multiple same-type and mixed-item Service Requests.
- Stock transaction history, Client File assignment, barcode printing, configured billing/rental surfaces, and applicable reports where available.
- Manual Asset Management creation for SafetyWatch, SafetyWatch 3, SmartTracker, SmartTracker 2.0, and SmartTracker 3.

## Out of Scope

- Barcode sequence length and characters after the configured prefix; the existing barcode generator owns that behavior.
- Mobile SOS, Mobile Carer, Portal Web, and CP Web behavior; no approved evidence identifies these as consumers.
- Production-only billing, printing, or report execution when safe isolated test data or the required surface is unavailable.

## Business Rules

1. Service Request SafetyWatch stock maps to SafetyWatch 3, not legacy SafetyWatch.
2. Service Request SmartTracker stock maps to SmartTracker 3, not SmartTracker or SmartTracker 2.0.
3. The generated barcode begins with the prefix configured for the mapped Asset Type: `SF3` or `ST3`.
4. One Generate Asset execution creates one asset for the correct checklist instance and cannot be repeated for that completed instance.
5. Existing `SAW` and legacy `ST` assets retain their original IDs, Asset Type IDs, barcodes, device links, and Client File relationships.
6. Manual Asset Management creation uses the explicitly selected Asset Type and its configured prefix.

## UI/UX Rules

- Generate Asset completes against the selected checklist instance and displays its generated barcode.
- Closing and reopening the Service Request retains the completed state and barcode.
- The generated device is assumed to retain the SafetyWatch or SmartTracker stock-type display name; the v3 version is proven through the asset record.

## Validation Rules

- Verify the configured Asset Type ID as well as the barcode prefix; prefix-only validation is insufficient.
- Verify the generated asset exists once and remains linked to the originating checklist and device.
- For multiple or mixed items, each checklist receives a unique barcode and asset ID without cross-linking.
- A completed historical or newly generated checklist cannot create a replacement or duplicate asset.

## Integration Impact

- Service Request Process, Asset Management, Stock Levels transaction history, and Client File device relationships must reference the same asset and barcode.
- Barcode print output, configured billing/rental consumers, and applicable reports must use the persisted v3 Asset Type when those surfaces are available.
- No notification, alert, FCM, SMS, email, Twilio, QuickBooks, or external submission behavior is confirmed for this change.

## Permissions / Roles

Approved cases use an authorised user who can create and process Service Requests, execute checklist steps, view Asset Management, and access the applicable downstream surface. Unauthorized-role behavior is not specified.
