## Requirement Summary

Add `L-Series Call Point F1`, `L-Series Fall Sensor F1`, and `L-Series Smoke Transmitter F1` to CP Stock Levels, Device Setup Steps, and Service Request Progress workflows. The same types must be accepted by the legacy and AWS stock backends. Setup-step availability and Client File resolution differ between independent peripherals and peripherals beneath `SmartHome LGX VFII Dialler`.

## Confirmed Scope

- CP Stock Levels and every existing manual transaction action for the three new Stock Types.
- Legacy and AWS Stock Type compatibility.
- CP Device Setup Steps for independent/top-level and LGX VFII child contexts.
- Service Request Progress checklist generation.
- Select Client File, Create Medi Alarm, and Listen for Alarm inherited workflows.
- Stock Level Report, Billing Defaults, and Service Request By TAG regression from the approved source suite.

## Out of Scope

- New security, performance, notification, billing-calculation, job, or queue behaviour is not introduced by the Jira requirement.
- Other peripheral types and diallers are unchanged except for negative compatibility verification.
- Exact internal endpoint, database object, queue, and log schemas are not supplied.

## Business Rules

1. The new Stock Types retain distinct identities and do not remap to another L-Series type.
2. Independent peripherals use Select Client File as the Client File source for Create Medi Alarm.
3. LGX VFII child peripherals use Assign to Client File on the parent device and do not add Select Client File to the child.
4. A wrong Client File or wrong Medi Alarm does not complete Listen for Alarm; an LGX VFII child also requires the correct parent/main device.
5. One accepted action produces one Stock Transaction, Medi Alarm, checklist item, or listener completion as applicable.
6. Total, Available, and On Order use R14–R16.

## UI/UX Rules

- The three friendly names appear once in applicable selectors, trees, reports, and TAG views.
- Device Setup presents the exact context-specific step sets defined by R7 and R9.
- Refresh and reopen preserve saved configuration and runtime state without creating duplicates.
- The exact hidden, disabled, or validation presentation for an unmet prerequisite remains an Open Question.

## Validation Rules

- Create Medi Alarm cannot be validly configured or completed before its applicable Client File prerequisite.
- Missing required CAMS fields prevent Medi Alarm creation without partial persistence.
- Zero-quantity Adjustment is rejected without Stock mutation or an accepted history record.
- Approved negative-Adjustment coverage is retained from Confluence v12; its broader reuse must remain within supported Stock behaviour.
