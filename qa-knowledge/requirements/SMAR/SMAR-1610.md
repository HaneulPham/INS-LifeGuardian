## Requirement Summary

SMAR-1610 removes `ClientFile.DeviceId` as the stored primary device/dialler reference. Code that needs a primary dialler or its status must query current device assignments at runtime. The change affects CP Desktop Client File listing/details, notification and Call entry points, Client File deletion, Portal Client List Device Status, Old SHM dispatcher contracts, alarm routing, and `AlarmSyncJob`.

The safety-critical outcome is that current assignments determine alarm ownership and primary-dialler behavior, stale historical `DeviceId` data does not control processing, and unmatched CAMS/SHM alarms route once to the designated unknown-file record.

## Confirmed Scope

- CP Desktop Client File listing, details, Status column, Create Notification, Delete, and Call.
- Current device/dialler assignment lifecycle, including Suspended, legacy-migrated, no-dialler, and mobile-only files where the final action is defined.
- CAMS/SHM alarm data and SMS routes listed in Jira, `AlarmSyncJob`, and unknown alarm routing.
- Old SHM `POST /api/dispatcher` request classes named in Jira.
- Portal Web Client List, Client Details, and dynamic Device Status.
- Release-note verification for the Client File `52001` rename.

## Out of Scope

- Deprecated `ReportClientFileBillingTransformer` and `DocumentFieldHistory_Transformer` runtime testing.
- Commented-out CP Client File list Call command and removed InteractionServices functions.
- Internal patcher scripts unless a previously required script is identified.
- Defining new primary-dialler ranking beyond the Jira-confirmed Portal Configured + OnSite rule and fallback.
- Production alarm delivery; use controlled non-production routes and evidence.

## Business Rules

1. Persisted `ClientFile.DeviceId` does not select the primary dialler after this change.
2. Current assignment relationships are the source for runtime dialler/file resolution.
3. CP Client File Status is independent of device status and dialler assignment.
4. A Client File with any assigned device cannot be deleted.
5. Call does not start when runtime resolution returns no callable device and shows the established no-device message.
6. A reassigned dialler routes subsequent alarms and Call behavior to its current Client File only.
7. Unmatched alarms on the Jira-listed routes use Client File `52001` and create no duplicate alarm.
8. Portal prefers a Configured + OnSite dialler, then falls back to any Configured dialler.
9. Removed dispatcher contract fields/search criteria must not reappear through stale consumers.

## UI/UX Rules

- CP Client File Status column retains only the Client File status.
- Client File and Portal lists remain searchable, pageable, and navigable after removal of the property.
- Missing-device Call attempts display the established user message without an unhandled exception.
- Client File `52001` displays `Alarms (Unknown File or Device)` in Client File and Alarm History views.

## Validation Rules

- Delete evaluates all current assigned devices, not a single stored identifier.
- Runtime primary-dialler resolution is refreshed after assignment changes and reopen/restart.
- Unknown alarms never attach to an unrelated Client File.
- `GroupUuids` must not return files solely because of a group match; exact rejection/ignore behavior requires confirmation.

## API / Backend Impact

- Old SHM dispatcher at `{{shm_domain}}/api/dispatcher` for the request types named in the approved page.
- Remove `DeviceId` from returned `ClientFileContract` data for `LoginWithPhoneNumberRequest`, `FindFilesRequest`, and `AssignClientFileRequest`.
- Remove `GroupUuids` search handling and corresponding AWS backend use.
- Assignment persistence uses device-to-file relationships and does not write a Client File primary-device field.
- Exact serialized success/error bodies remain partially unverified beyond the Jira-confirmed field removal.

## Integration Impact

- CP Desktop and Portal use current assignment data.
- CAMS/SHM alarm services and `AlarmSyncJob` must converge on the same Client File association.
- AWS backend consumers must stop sending/using `GroupUuids` for the removed search path.
- No new FCM, SMS, email, Twilio, billing, or export behavior is introduced by the Client File configuration change; alarm transport itself remains in scope.

- Existing tenant, village, and Client File boundaries remain enforced.
- Direct API and alarm evidence must use isolated non-production records and must not expose client or contact details.
