## Requirement Summary

SMAR-2650 closes an authentication gap in SmartHome.Functions.ActMonitoringCriteria. The file-level POST, GET, PUT, and DELETE routes currently require an API key but are not protected by HmacHashApiGatewayAuthorizer. The change adds the shared HMAC authorizer to all four routes while retaining API-key enforcement and the existing Activity Monitoring Criteria CRUD contract.

Approved coverage contains 12 cases across source/deployment configuration, valid dual-authentication CRUD regression, and rejection when either or both authentication layers are missing or invalid.

## Confirmed Scope

- SmartHome.Functions.ActMonitoringCriteria file-level version 2 routes: POST file, GET file/{Uuid}, PUT file, and DELETE file.
- Source serverless.yml, generated infrastructure, active API Gateway stage, and effective route inventory.
- Additive HMAC and API-key enforcement.
- Existing authenticated CRUD responses, persistence, record targeting, and non-target integrity.
- Rejection before successful business-handler processing and without protected-data or credential disclosure.

## Out of Scope

- Redesigning the shared HMAC algorithm, authorizer, credential lifecycle, or API-key mechanism.
- Changing Activity Monitoring Criteria business schemas, validations, scheduling, analysis logic, or ordering.
- Unlisted device-level or non-file Activity Monitoring Criteria routes.
- Production secrets or production client data.
- Production-only infrastructure inspection when equivalent sanitized test-stage evidence is available.

## Business Rules

1. Every listed route requires both a valid API key and valid HmacHashApiGatewayAuthorizer authorization.
2. Valid HMAC does not bypass a missing or invalid API key.
3. A valid API key does not bypass missing or invalid HMAC.
4. Rejected requests do not return HTTP 200, criteria data, or the normal CRUD success contract.
5. Rejected POST, PUT, and DELETE requests create no partial, duplicate, updated, or deleted criteria record.
6. Valid dual-authenticated requests retain the established HTTP 200 CRUD behaviour.
7. Exactly one effective protected method exists for each method/path combination in the active stage.
8. Authentication responses, logs, screenshots, and exports do not expose reusable secrets, signatures, complete API keys, stack traces, or unnecessary client information.

## UI/UX Rules

None. This is a Backend API and deployment-security change.

## Validation Rules

- HMAC must be generated for the exact method, path, canonical query string where applicable, timestamp, and request body according to the deployed contract.
- Missing and deliberately altered HMAC variants are rejected.
- Missing and unrecognized API-key variants are rejected.
- Both credentials absent is rejected.
- Exact numeric rejection status, body, and headers must be derived from an established endpoint already protected by the same authorizer; they are not hardcoded by this ticket.

## API / Backend Impact

- Add the HMAC authorizer to four HTTP events in serverless.yml.
- Retain the existing API-key/private-route property.
- Preserve methods, paths, path parameter {Uuid}, handler mappings, environment variables, timeouts, request schemas, and success responses unless separately documented.
- Deployed API Gateway methods must resolve to the intended HMAC authorizer and current handler.
- No duplicate, legacy, stale, or alternate method may provide an API-key-only bypass.

## Integration Impact

- Existing authenticated callers must add valid HMAC while continuing to send the API key and DeviceUuid required by the established contract.
- The shared API Gateway authorizer is the affected security integration.
- No new FCM, SMS, email, Twilio, billing, alarm, or notification integration is confirmed.

## Permissions / Roles

- This ticket changes gateway authentication, not application roles.
- Test credentials must be authorized for the target non-production environment.
- Authentication failure must not disclose client-file existence or criteria data.

## Background Jobs / Queues

No new job or queue is confirmed. Rejected requests must not reach normal handler processing that could create or alter downstream scheduling work.

## Audit / History / Logs

- Capture sanitized gateway/authorizer and handler-entry evidence using a correlation identifier where supported.
- Developer/operations evidence must distinguish gateway rejection from handler execution.
- Logs must mask HMAC material, full API keys, reusable signatures, and unnecessary client data.
- Valid GET does not modify audit fields; valid PUT updates only the established updater fields; rejected requests create no accepted-business audit event.

## Reports / Export Impact

None confirmed. Rejected writes must not create data later visible in reports or exports.

## Cross-Platform Sync Impact

No direct UI change is confirmed. Any existing caller of the four routes must continue to receive the established response after sending both authentication layers; rejected requests must not create stale or divergent criteria state.

- Rejection responses must not expose criteria content, record existence, signing inputs, stack traces, or authorizer configuration.
