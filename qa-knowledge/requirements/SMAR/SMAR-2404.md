## Requirement Summary

SMAR-2404 removes SafetyWatch from the response transformation that substitutes an Asset Barcode into `LineNumber` when the stored LineNumber is blank. A returned SafetyWatch must expose its stored LineNumber when populated and a blank LineNumber when not populated. The existing SmartHomeMini/Mobile Barcode fallback remains unchanged.

The shared behavior affects `GetDeviceRequest`, `GetDeviceByLineNumberRequest`, `DeviceTransformer`/`FindDevicesRequest`, CP Device Listing and Client File device loading, device billing and linking-code consumers, Billing Reports, and the Twilio incoming-message alarm path. Exact downstream outcomes not stated by Jira remain gaps rather than confirmed requirements.

## Confirmed Scope

- `GetDeviceRequest` SafetyWatch and SmartHomeMini/Mobile response mapping.
- `GetDeviceByLineNumberRequest` lookup by a unique stored LineNumber and unmatched values.
- `DeviceTransformer`/`FindDevicesRequest` output used by CP Device Listing.
- CP Device Listing SIM Number display for populated and blank LineNumber states.
- Twilio Incoming Message regression for a unique valid SafetyWatch LineNumber and existing SmartHomeMini/Mobile behavior.
- Protection against wrong-device and cross-client alarm association.
- Jira-named downstream regression areas: device billing GET/PATCH, linking-code assignment, billing online/offline behavior, CP Billing, Billing Report, and CP Client File device loading.

## Out of Scope

- Changing how SafetyWatch Asset Barcodes are generated or persisted.
- Changing the stored SafetyWatch LineNumber or creating a new LineNumber value.
- Removing the confirmed SmartHomeMini/Mobile Barcode fallback.
- Changing alarm content, escalation, notification recipients, or acknowledgement/restoral behavior beyond device resolution.
- Defining new SIM-provider rates, billing amounts, or linking-code rules.

## Business Rules

1. SafetyWatch Asset Barcode is a system-generated asset identifier and is not a valid substitute for SafetyWatch LineNumber.
2. A populated SafetyWatch LineNumber takes precedence over Asset Barcode in returned device data.
3. A blank SafetyWatch LineNumber remains blank in returned/transformed data.
4. SmartHomeMini/Mobile keeps the existing Barcode fallback when its LineNumber is blank.
5. Lookup and alarm tests must use unique values and verify DeviceUuid plus client-file association; related SMAR-2403 evidence showed duplicate phone values can select a different device.

## UI/UX Rules

- CP Device Listing SIM Number displays the stored SafetyWatch LineNumber when populated.
- When SafetyWatch LineNumber is blank, SIM Number uses the existing blank/unset presentation and must not show Asset Barcode.
- SmartHomeMini/Mobile SIM Number continues showing stored LineNumber or its confirmed Barcode fallback.
- Exact Client File device-screen blank presentation is not supplied.

## Validation Rules

- Test populated and blank SafetyWatch LineNumber states separately.
- Use a Barcode value different from the stored LineNumber.
- Use unique stored LineNumbers and Barcodes that do not collide with another device.
- Use an unassigned valid-format lookup value for negative resolution coverage.
- Do not treat the disputed SafetyWatch-by-Barcode result as executable until the conflict is resolved.

## API / Backend Impact

- Dispatcher endpoint: `POST /api/dispatcher`.
- Affected request classes: `GetDeviceRequest` and `GetDeviceByLineNumberRequest`.
- `DeviceTransformer` is used by `FindDevicesRequest` and downstream CP/Billing consumers.
- Exact authentication package, accepted status, not-found status/body, error envelope, and response schema are not fully supplied in the reviewed evidence.
- Positive cases record the deployed accepted status; negative cases verify the absence of an incorrect device payload while capturing the deployed not-found contract.

## Integration Impact

- `GetDeviceRequest` supports GET Device Billing, PATCH Device Billing, and POST Device Linking Code.
- `GetDeviceByLineNumberRequest` supports POST Twilio Incoming Message device resolution.
- `DeviceTransformer`/`FindDevicesRequest` supports CP Device Listing, CP Client File device loading, and GET Device Billing by File/Group.
- A wrong lookup must not create an alarm for another device, client file, or tenant.

## Permissions / Roles

Use existing authorized CP device-list access and approved non-production API/Twilio authentication. Exact role names and permission-denial behavior are not changed or supplied by SMAR-2404.

## Background Jobs / Queues

No new background job or queue behavior is confirmed. Existing downstream alarm or billing processing must not be duplicated by repeated reads or screen loads.

## Audit / History / Logs

- For alarm cases, capture the resulting controlled alarm identifier and client/device association.
- Exact log fields and audit-event contracts are not supplied and may require developer or operations support.
- Never store credentials, real phone numbers, or client personal/medical data.

## Cross-Platform Sync Impact

Backend API and CP Desktop Device Listing must represent the same SafetyWatch versus SmartHomeMini/Mobile LineNumber mapping. No CP Web, Portal, or Mobile UI change is stated.

## Privacy / Sensitive Data Impact

Use synthetic non-production client files, devices, numbers, credentials, and alarm content. Evidence must identify records through privacy-safe test aliases/correlation IDs and must not expose client contact, medical, authentication, or tenant data.

## Regression Risk

SafetyWatch LineNumber mapping is shared by dispatcher device reads, device lookup, CP device/client-file loading, billing provider/rate selection, linking-code assignment, Billing Reports, and Twilio alarm routing. Regression must protect the SmartHomeMini/Mobile Barcode fallback, correct device/client association, blank-versus-Barcode presentation, no response-time persistence mutation, and no missed, duplicate, or wrong-client alarm.
