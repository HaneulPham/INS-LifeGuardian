## Requirement Summary

SMAR-2538 adds HTTP Strict Transport Security to the API Gateway path for `https://devapi.inslifeguard.com`. The header must be present on normal backend responses and on responses generated by API Gateway before a request reaches the backend. The change must preserve the original HTTP status and response body.

The approved source verifies a representative 2xx response, both gateway-generated and backend-generated 4xx responses, and a genuine 5xx response. The 5xx objective cannot be executed safely until Development or Operations supplies a controlled failure mechanism.

## Confirmed Scope

- HTTPS requests to `devapi.inslifeguard.com` or the corresponding deployed non-production API domain covered by the change.
- A valid Task API request returning its documented 2xx outcome.
- An undefined route rejected by API Gateway with a 4xx outcome.
- A defined Task API route reaching backend validation and returning a 4xx outcome for an invalid `ClientUuid`.
- A genuine controlled 5xx response once a safe test mechanism is supplied.
- Complete response-header, status, and body capture proving that the original response remains intact.

## Out of Scope

- Adding the `preload` directive or submitting a domain to the browser preload list.
- Portal and Control Panel frontend HSTS behavior; the ticket scope identifies the API domain.
- Breaking or disabling shared infrastructure solely to create a 5xx response.
- Broad API functional regression beyond proving that representative response status/body behavior is preserved.

## Business Rules

1. HSTS must be applied consistently whether a response originates from the backend or API Gateway.
2. The header change must not convert the response to another status class or replace the normal response/error body.
3. The response must not contain conflicting HSTS values.
4. Absence of `preload` is not a failure for this ticket.

## UI/UX Rules

## Validation Rules

- Capture complete response headers rather than relying on the response body or browser behavior.
- Confirm the undefined test path is not an application route before using it as API Gateway 4xx evidence.
- Use valid endpoint authentication for the backend-validation case so an upstream authentication rejection does not replace the intended backend 4xx.
- A malformed request that correctly returns 4xx is not valid evidence for the deferred 5xx objective.

## API / Backend Impact

- Backend responses require HSTS injection.
- API Gateway response configuration requires the same header for responses that do not reach backend processing.
- The approved 2xx and backend 4xx cases use `GET /shm/task/v2/{ClientUuid}` as representative coverage.
- Exact infrastructure implementation details are not required for tester execution unless needed to prove response origin.

## Test Data, Isolation, and Cleanup

- Use an accessible synthetic `ClientUuid` for the valid 2xx case.
- Use an intentionally invalid GUID-shaped or non-GUID value only on the defined backend-validation route.
- Confirm the undefined gateway route cannot mutate application data.
- The approved calls are read-only; no data cleanup is expected.
- Any future 5xx fixture must use an isolated, reversible mechanism approved by Development or Operations.

## Required Test Instrumentation

- An API client capable of showing complete response headers without automatically hiding redirects or intermediate responses.
- Gateway/backend evidence proving that `SMAR-2538-G2-02` reached backend processing.
- A named endpoint, HTTP method, controlled failure trigger, expected 5xx status, and response capture for deferred `SMAR-2538-G3-01`.

## Regression Risk

Shared response handling can omit HSTS on gateway errors, add conflicting duplicate values, or alter normal status/body behavior. Recheck representative backend and gateway response origins across 2xx, 4xx, and safely controlled 5xx classes.

## Confirmed Decisions
