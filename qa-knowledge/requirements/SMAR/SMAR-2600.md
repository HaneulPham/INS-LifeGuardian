## Requirement Summary

SMAR-2600 prevents CP Web users from creating or updating DVA Work Orders and updating DVA Invoices when required identity, address, or delivery values are blank. The required values under review are Client First Name, Client Last Name, Client/Invoice Postcode, Client/Invoice Address, Delivery Postcode, and Delivery Address.

The defect was observed after an incomplete Client File supplied a blank Postcode to a Work Order; the downstream invoice batch then failed DVA validation. This ticket enforces requiredness only. It does not add postcode format, numeric-only, or valid-State validation.

## Confirmed Scope

- CP Web Work Orders → Work Order Management → Add → Client & Delivery.
- CP Web editing an existing Work Order through Client & Delivery.
- CP Web editing an existing Invoice.
- Required-field validation triggered by Save/Next.
- Positive save and reopen for complete data.
- One-at-a-time blank validation for each of the six named values.
- Rejected create/update persistence protection and correction/retry.

## Out of Scope

- Numeric-only postcode validation.
- Recognition or rejection of valid/invalid State values.
- Any other address-format, length, or character validation not required to prove a value is present.
- Automatic production-data repair or migration; no migration rule is supplied.

## Business Rules

1. Save/Next must not complete a Work Order create, Work Order update, or Invoice update while an applicable mandatory value is blank.
2. The user must be able to identify the missing field and provide a value.
3. After correction, the same create/update workflow may complete and the submitted values must remain after reopen.
4. A value that is present but invalid only by postcode format or State validity is not rejected by SMAR-2600 requiredness logic.

## UI/UX Rules

- Validation is visible against or clearly associated with the applicable missing field.
- Exact text, punctuation, styling, focus order, and whether all missing fields appear in one attempt are not confirmed.
- `Save/Next` is the supplied validation trigger.

## Validation Rules

- Confirmed invalid class: a blank applicable mandatory value.
- Null, whitespace-only, and copied/inherited empty-value treatment are not explicitly defined and require execution evidence or a product decision.
- Valid nonblank values permit progression when all other normal workflow requirements are satisfied.
- State/postcode format validation must not be inferred from this ticket.

## Open Questions

1. Does validation apply only to DVA-eligible Work Orders/Invoices, or to every record exposing these fields?
2. What exact message, styling, and focus behavior identifies each missing field?
3. Must all missing fields be identified in one Save/Next attempt, or may validation progress one field at a time?
4. When Same As Client Details is checked, are Delivery Address/Postcode copied, inherited dynamically, or validated separately?
5. May an historical incomplete record be viewed and saved only after correction, or may unrelated edits persist without correcting it?
6. Does correcting Work Order or Invoice data update the source Client File, remain local, or depend on the field?
7. Must backend APIs enforce the same fields, and what are the deployed routes and error contracts?
8. How are null and whitespace-only values treated compared with a visually blank field?
