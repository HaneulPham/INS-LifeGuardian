## Requirement Summary

The Old SHM backend currently allows `RaiseAlarmRequest` and `GetClientFileRequest` to authenticate through `BasicAccessAttribute` with `x-api-key` alone. SMAR-2638 removes the attribute and associated fallback logic from SmartHome and SmartHome Alarm. The legacy authentication path must require a valid HMAC Hash. Requests containing only `x-api-key`, no authentication, an empty/malformed HMAC, or a cryptographically invalid HMAC must be rejected before protected business handling.

Valid HMAC calls remain supported. `GetClientFileRequest` also retains its confirmed OAuth path from SMAR-2658. Accepted alarm calls create one controlled alarm per unique correlation ID; rejected alarm calls create none. Accepted client-file calls are read-only and return only the authorized client file; rejected calls expose no client-file data or existence signal.

## Confirmed Scope

- SmartHome.Component port `4444` and SmartHome.Alarm.Component port `4454`.
- `POST /api/dispatcher` for `RaiseAlarmRequest` and `GetClientFileRequest`, pending deployment confirmation.
- Removal of basic-access and `x-api-key`-only authentication for the two requests.
- Valid HMAC compatibility and existing OAuth compatibility for `GetClientFileRequest`.
- Rejection before handler entry, protected-data return, alarm creation, or downstream processing.
- Sanitized authentication logging and no credential disclosure.

## Out of Scope

- OAuth issuance, claims, permissions, or tenant authorization changes.
- HMAC algorithm redesign or production credential rotation.
- Changes to accepted request business schemas.
- Platform-wide penetration testing.
- Production alarm execution.
- Missing Group 4 response-field coverage until supplied or separately approved.

## Business Rules

1. `x-api-key` without a valid HMAC must not authenticate either request.
2. Missing, empty, whitespace-only, malformed, truncated, wrong-secret, and tampered HMAC values must not activate fallback access.
3. Valid HMAC requests continue through unchanged authorization and business rules.
4. Each accepted alarm request creates one response and one controlled alarm for its unique correlation ID.
5. Rejected alarm calls create no alarm ID, alarm record, CP alarm, queue message, notification workflow, or downstream action.
6. Accepted client-file calls return only the authorized file and perform no write.
7. Rejected client-file calls return no protected client/device/contact/care/tenant data or record-existence signal.
8. Responses and logs must not expose API keys, HMAC values, signing strings, secrets, OAuth tokens, or unnecessary client information.

## UI/UX Rules

- No direct UI change is confirmed.
- Existing supported clients using OAuth or valid HMAC retain their current client-file loading/synchronization flow.
- Authentication errors must not expose protected client or alarm details.

## Validation Rules

- HMAC must be present and cryptographically valid for the exact deployed signing contract.
- Empty/whitespace, malformed/truncated, wrong-secret, and tampered signatures are rejected.
- Rejected requests do not return HTTP `200` with `RaiseAlarmResponse` or `GetClientFileResponse`.
- Exact HMAC header names, timestamp tolerance/replay rules, and numeric failure contract remain open.

## API / Backend Impact

- Remove the attribute and fallback logic from both request classes in both components.
- Preserve HMAC validation and the existing handlers after accepted authentication.
- Preserve the confirmed OAuth path for `GetClientFileRequest`.
- Old SHM source was not present in this workspace, so class wiring and deployed configuration could not be independently verified.

- Exact queue, callback, provider, and notification identifiers require instrumentation.

## Permissions / Roles

- Tests use synthetic non-production clients/devices.

## Background Jobs / Queues

- Rejected alarm calls enqueue no alarm processing.
- Rejected client-file calls create no callback, notification, or unrelated job.
- Exact internal names remain unverified.

## Regression Risk

- Critical safety risk if valid alarm calls are blocked.
- High security/privacy risk if `x-api-key` alone still authenticates.
- High compatibility risk across existing HMAC/OAuth consumers.
- High data-integrity risk if rejected calls create alarms or mutate client files.
- Medium operational risk if failures cannot be correlated safely.

## Confirmed Decisions
