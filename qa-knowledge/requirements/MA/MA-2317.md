## Requirement Summary

MA-2317 redesigns Mobile SOS onboarding and registration for logged-out users. The current linked acceptance-criteria page defines introduction and routing, self-setup and carer handoff, returning-user authentication, OTP and recovery, new-user profile creation, plan/referral/callback routes, resume behavior, final routing, and data persistence on supported iOS and Android builds.

The user-supplied page is retained as historical conflict evidence only. Its 27 executable and 3 skipped items are not copied as a second suite because the newer MA-2317 page contains the current executable coverage and materially changes prior scope.

## Confirmed Scope

- Mobile SOS onboarding and registration on supported iOS and Android builds.
- Logged-out introduction, route selection, self-setup, returning-user login, and LifeGuardian Connect handoff.
- OTP request, verification, resend, account-not-found recovery, device selection, and account reactivation.
- New-user profile/questionnaire, simulated alarm education, profile creation, plan/referral/promo/callback routes, and final Home routing.
- Offline/failure recovery, duplicate-action prevention, resume after interruption, and final registration-data persistence.
- Privacy-safe verification of account, Client File, device, billing, callback, alarm-isolation, and notification evidence only where named by the source case.

## Out of Scope

- Wearable onboarding, per the supplied mirror.
- Unspecified internal endpoint paths, payload fields, database schemas, analytics event fields, queue names, provider contracts, and audit formats.
- Importing source execution-result columns as reusable expected behavior.
- Reusing supplied test phone numbers, account identifiers, Client File identifiers, or other sensitive execution data.

## Business Rules

1. Post-authentication and post-registration routing depends on the authenticated account, Client File, eligible device, billing, referral/promo, deactivation, and onboarding-completion state defined by the current source case.
2. One user action must not create duplicate OTP requests, screens, registrations, subscriptions, callback requests, billing records, alarms, or notifications.
3. Failed or interrupted operations must not display false completion or create partial persisted state.
4. The onboarding alarm experience is a simulation and must not become a real alarm, activity, notification, escalation, call, queue event, or restoral.
5. Registration and recovery data must remain isolated to the correct non-production account and Client File.

## UI/UX Rules

- Current MA-2317 screen content, enabled actions, navigation, Back behavior, safe-area layout, and accessibility expectations are defined by the v218 case rows.
- Exact design-copy assertions remain source-case-specific and must be compared with the approved design/copy source when available.
- Legacy or unrelated screens must not be shown where the case requires a specific onboarding destination.

## Validation Rules

- Phone, OTP, name, profile, questionnaire, device, referral/promo, and plan inputs follow the validation outcomes named in the applicable current source case.
- Invalid, expired, duplicate, incomplete, offline, or failed actions must not create false accepted state or unrelated downstream records.
- Exact API error schemas and numeric statuses remain Open Questions unless a case names tester-accessible evidence.

- Current source cases observe authentication, account resolution, Client File/device selection, registration/profile persistence, billing/subscription, callback, and alarm-isolation effects.
