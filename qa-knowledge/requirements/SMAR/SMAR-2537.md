## Requirement Summary

Add **Select Client File**, **Create Medi Alarm**, and **Listen for Alarm** to Device Setup Steps and Service Request Process for the confirmed peripheral sets. Eligibility and Client File source depend on whether a peripheral is top-level or under a parent device. Create must persist a CAMS or INS device against the correct File and Client, Listen must match the intended alarm context, and Service Request-initiated removal must delete the generated device without making direct Client File deletion rewrite the Service Request.

## Confirmed Scope

- CP Desktop Settings → Device Setup Steps and Client File → Service Requests → Process.
- The 18 Jira-listed non-PIR supported peripherals, PIR, and representative unsupported peripherals.
- Top-level and child topology, parent Client File inheritance, CAMS and INS creation, persistence, placement, Listen matching, and removal lifecycle.
- Refresh, reopen, restart, duplicate-prevention, failure-isolation, and existing-control regression from the reviewed QA suite.

## Out of Scope

- New Mobile UI, Portal Web UI, notification, billing, report, export, job, or queue behaviour is not introduced by SMAR-2537.
- New role or permission rules are not defined by the ticket.
- Exact internal API routes, database objects, error payloads, timeout durations, and provider-log schemas are not supplied.

## Business Rules

1. Eligibility is determined by peripheral type and topology; a child never receives its own Select Client File step.
2. The Client File used for Create is the persisted top-level selection or the main parent assignment, not whichever Client File is currently open in CP.
3. CAMS and INS create one type-appropriate device on the resolved Client File; an unrelated Client File and the other device category remain unchanged.
4. A Listen result belongs only to the matching File, topology, and Medi Alarm UUID context.
5. Removal direction is asymmetric as defined by R10.

## UI/UX Rules

- Each eligible step appears once and unsupported steps remain absent.
- Select and Create remain unavailable until their confirmed required inputs and prerequisites exist.
- Saved setup and Process state persist after refresh and reopen without duplicate steps or generated devices.
- Exact validation text and the hidden-versus-disabled prerequisite presentation remain Open Questions.

## Validation Rules

- Reject invalid ordering, missing required fields, missing topology-specific Client File prerequisites, duplicate steps, and unrelated alarm contexts without false completion or partial persistence.
- Zone No is the CAMS display label for the underlying Location value described by Jira.
- Exact error messages and status labels must be captured from the supported build; they are not invented here.

## API / Backend Impact

- Persist Device Setup step type/order/model, Service Request selected Client File, generated device UUID/linkage, and Listen state.
- Match the alarm legacy `RecivedFromMediAlarmDeviceId` value against the generated Medi Alarm UUID.
- Exact endpoints, methods, request/response schemas, transaction boundaries, and error contracts are Open Questions.

## Integration Impact

- CAMS and INS device creation/removal and alarm receipt/matching are affected.
- Wrong-file, wrong-parent/topology, or wrong-Medi-Alarm alarms must not complete the active listener.
- No new FCM, SMS, email, Twilio, billing, report, or export trigger is confirmed.

## Permissions / Roles

Use existing authorized Device Setup, Service Request, Client File, CAMS, and INS access. New authorization or tenant rules are not defined; privacy-safe File isolation remains required.

## Background Jobs / Queues

None confirmed. Provider processing or listener infrastructure may be asynchronous, but exact jobs, queues, retries, and timeout contracts require supported evidence.

## Audit / History / Logs

- Tester-accessible evidence: Device Setup values/order, Service Request Process state, selected File number/name, Client File device tabs, generated UUID, refresh/reopen state, and controlled alarm result.
- Developer/operations-supported evidence: provider create/delete failure, active listener correlation, alarm matching identifiers, concurrent sessions, cancellation, timeout, and partial-write checks when UI evidence is insufficient.
- Do not store client identity, contact/health data, credentials, or tenant secrets in evidence.

## Reports / Export Impact

None confirmed.

## Cross-Platform Sync Impact

CP Desktop is the confirmed UI. Mobile backward compatibility is limited to retaining the legacy alarm field contract in R13; no Mobile UI change is confirmed.

## Privacy / Sensitive Data Impact

- Use synthetic non-production Client Files, owners, device descriptions, zones/locations, and alarm identifiers.
- Wrong-File tests verify isolation without exposing another client's identity or sensitive information.
- Redact UUIDs and support logs when they can identify production records.

## Test Data, Isolation, and Cleanup

- Use isolated top-level and child configurations, two privacy-safe Client Files, CAMS and INS models, unique descriptions, and controlled matching/mismatching alarms.
- Record original Device Setup configuration and restore only test-created steps through supported UI actions.
- Remove test-created devices through the scenario-approved path; preserve required audit/correlation evidence and never delete unrelated Client File records.

## Required Test Instrumentation

- Controlled CAMS/INS create and delete failures.
- Controlled alarms varying File, top-level/parent context, and Medi Alarm UUID.
- Correlation/log evidence for duplicate, concurrent, timeout, cancellation, and late-alarm handling when UI state cannot prove the outcome.
- Persisted linkage or provider evidence for failure atomicity without direct production-data inspection.

## Regression Risk

SMAR-2537 changes shared Device Setup, Service Request Process, Client File device placement/removal, CAMS/INS creation, and alarm matching. A topology or Client File source error can create a safety device on the wrong File or accept the wrong alarm; duplicate and stale processing can leave inconsistent Service Request/device state. Dedicated regression relationships are recorded in the regression map.

## Confirmed Decisions

DEC-024 is reused for the SMAR-2683 F1 subset: independent peripherals use Select Client File, while SmartHome LGX VFII child peripherals use the parent Assign to Client File context. No new decision record is required for the broader Jira-confirmed SMAR-2537 rules.
