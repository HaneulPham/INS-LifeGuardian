## Requirement Summary

The Old Backend dispatcher must enforce OAuth-only authentication for eighteen specified request classes. A valid legacy HMAC request without OAuth must be rejected before protected business logic runs. Three request classes remain dual-authentication exceptions because current AWS, device, or mobile consumers still depend on HMAC: `FindDevicesPortalRequest`, `FindFilesPortalRequest`, and `GetClientFileRequest`.

The change must not alter established OAuth authorization, validation, response data, or business outcomes. Rejected requests must use the existing Old Backend sanitized authentication-failure contract and must not create partial writes, audit mutations, status changes, relationship changes, jobs, notifications, or downstream provider activity.

## Out of Scope

- Replacing HMAC for the three exception request classes.
- Changing OAuth token issuance, claims, roles, tenant permissions, or expiry behaviour.
- Changing business validation or response data for accepted OAuth requests.
- General penetration testing or a platform-wide authentication redesign.
- CP Web client regression for this active ticket, following user decision Q1-B.
- Defining a mixed-credential precedence rule without BA/Product/Dev confirmation.

## Business Rules

1. Any OAuth-only request without a valid OAuth token is rejected even when its HMAC material is valid.
2. A valid OAuth request continues through the existing authorization, tenant, validation, and business rules.
3. Each named exception accepts its currently supported OAuth path and HMAC integration path.
4. Authentication rejection occurs before protected read data is returned or write business logic runs.
5. A rejected write creates no partial record, relationship change, status transition, audit-success entry, notification, job, or external-provider call.
6. Authentication failure responses do not disclose whether an HMAC signature, key, OAuth token, tenant, or protected record identifier was valid.
7. Mixed valid/invalid credentials on an exception route have no approved outcome until Q3 is decided.

## UI/UX Rules

- CP Desktop and Portal Web workflows that use OAuth must retain their existing navigation, content, validation, loading, and completion behaviour.
- A rejected or expired OAuth call must display the platform’s existing sanitized authentication/session handling and must not display protected data or false completion.
- The ticket adds no HMAC controls or credential fields to either client.

## Validation Rules

- HMAC-only calls to OAuth-only classes are rejected.
- The three exceptions retain both supported authentication paths.
- Existing role, tenant, resource, and request validation continues after authentication.

Open:

- Whether malformed extra credential headers are ignored or cause rejection when the primary supported credential is valid.

## API / Backend Impact

- Authentication selection is expected to be enforced centrally in or before `DispatchController`, based on the Jira developer note.
- Request-class classification must contain exactly eighteen OAuth-only classes and three exceptions.
- Existing request handlers and response schemas remain unchanged after authentication succeeds.
- The approved source suite uses `{{domain}}/api/dispatcher` with `POST` as a placeholder. The current route configuration and class mapping must be verified before execution.

## Integration Impact

- AWS integrations must continue to call the three exception requests using current HMAC authentication.
- Existing device and mobile consumers of `GetClientFileRequest` must continue to load or synchronize their assigned client file.
- Rejected Community News publishing, address-change, file-group, access-detail, procedure, and concierge writes must not start their established downstream workflows.
- Exact downstream events, providers, and queue names are implementation-dependent and must not be inferred.

## Permissions / Roles

- OAuth success cases require a user with the existing role, tenant, and resource permissions.
- Authentication success does not bypass authorization; wrong-role, cross-tenant, and wrong-resource requests remain rejected under the established contract.
- No response may reveal whether an inaccessible tenant, group, client file, device, or record exists.

## Background Jobs / Queues

- No new job or queue is introduced by the requirement evidence.
- Rejected write requests must not enqueue or schedule any related workflow.
- Exact affected job and queue names could not be verified.

## Audit / History / Logs

- Rejected requests may create a sanitized security/authentication log according to existing policy, but must not create a successful business-action audit entry.
- Approved evidence must correlate the dispatcher decision with the absence of business handler, persistence, audit-success, and downstream activity.
- Logs, screenshots, and exports must mask OAuth tokens, HMAC material, internal hosts, tenant identifiers, and unnecessary client data.

## Reports / Export Impact

- No direct report or export change is confirmed.
- Reports and exports must not show data changes from rejected write requests.

## Cross-Platform Sync Impact

- Accepted CP Desktop and Portal Web OAuth actions remain visible through their existing refresh or synchronization behaviour.
- Rejected requests create no false cross-platform update.
- Existing AWS/device/mobile synchronization remains in scope only for the three exception requests.

## Privacy / Sensitive Data Impact

- Authentication errors must not include tokens, HMAC material, credential-validation details, internal stack traces, or protected client, group, address, device, or tenant data.
- Test evidence must use synthetic non-production records and masked identifiers.

## Test Data, Isolation, and Cleanup

- Use isolated synthetic tenants, users, client files, groups, devices, news, concierge services, addresses, and change requests.
- Use two independent records for accepted and rejected write variants so that a valid OAuth action cannot hide a rejected HMAC-only mutation.
- Isolate notification recipients and external providers. Remove disposable records without deleting unrelated data or required audit evidence.
- Do not store real authentication values in screenshots, logs, requests, or the QA Second Brain.

## Required Test Instrumentation

- Verified request-class-to-route/method/body mapping.
- Sanitized dispatcher authentication decision showing the selected authentication path.
- Handler-entry or mock evidence proving rejection occurs before business logic.
- Persistence and audit queries for before/after state on rejected writes.
- Isolated event, job, queue, or provider evidence for affected downstream actions.
- Correlation identifiers that do not expose authentication or client data.

## Regression Risk

- High security risk if any OAuth-only class still accepts HMAC-only authentication.
- High compatibility risk if one of the three exceptions is accidentally made OAuth-only.
- High data-integrity risk if rejected writes reach business logic or downstream workflows.
- Medium client risk across CP Desktop and Portal Web if existing OAuth calls, session handling, filtering, permissions, or response parsing change.
- Medium privacy risk if authentication responses distinguish credential validity or expose protected data.

## Confirmed Decisions

- DEC-005: For SMAR-2658, client workflow regression covers CP Desktop and Portal Web. This replaces the Jira/Confluence CP Web wording for the active QA scope.
- DEC-006: Authentication failures use the existing Old Backend response envelope and contract; QA must not hardcode `401 Unauthorized` without verified implementation evidence.
