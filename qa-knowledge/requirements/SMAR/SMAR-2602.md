## Requirement Summary

SMAR-2602 replaces Primary-then-Failover try/catch behavior used by AWS Lambda calls to the old backend. The new `INSFailover` Parameter Store setting selects one route before execution: `false` uses Primary and `true` uses Failover. The non-selected route is not contacted. This prevents the Lambda timeout from expiring while waiting for Primary before attempting Failover and simplifies disaster-recovery switching.

The approved suite covers 15 affected requests in both states. Group 1 verifies Primary-only accepted outcomes. Group 2 uses an approved non-resolvable Staging Failover hostname and verifies controlled failure, Primary non-contact, and no partial, duplicate, stale, or false-completion business outcome.

## Confirmed Scope

- Parameter Store routing for `InsService` and `InsSmsService`.
- Exactly one selected old-backend route and no cross-route fallback.
- Requests: `GetDeviceByReference`, `GetDeviceByLineNumber`, `GetDevicesByReferences`, `GetDevicesByFile`, `GetDevicesByGroup`, `GetClientFile`, `GetReport`, `RaiseDeviceAlarm`, `CloseAlarm`, `ReassignFileGroup`, `LoginWithPhoneNumber`, `GetActiveAlarms`, `CancelAlarm`, `CreateFollowUp`, and `InsSmsService.Send`.
- Billing, Twilio inbound SMS, reports, alarms, file reassignment, Mobile account cancellation, nursing follow-up, and outbound SMS.
- Data integrity, duplicate prevention, retry observability, routing evidence, release notes, and failover-process follow-up.

## Out of Scope

- Automatic fallback; Jira explicitly removes it.
- Redesign of existing schemas, validations, billing calculations, alarm rules, reports, templates, or recipient rules.
- Production failover execution or production delivery.
- Storage of internal URL values, credentials, tokens, client/contact identities, or sensitive configuration.

## Business Rules

1. `false` sends an affected request to Primary only; `true` sends it to Failover only.
2. A selected-route failure does not retry the non-selected route.
3. The default is `false`.
4. One trigger creates at most one old-backend attempt and one accepted downstream outcome.
5. Failure creates no Completed UI/API state, partial data, cached-as-current result, accepted alarm/report/message/session/follow-up, or delayed silent request to the other route.
6. Existing outcomes remain unchanged when Primary is selected and available.
7. Release notes describe the setting and the operational failover-process owner is notified.

## UI/UX Rules

- No end-user setting is confirmed; this is operational configuration.
- Existing workflows retain their established Primary outcome.
- Invalid selected Failover shows or records each workflow's existing controlled failure without claiming completion.
- Exact error text is not confirmed.

## Validation Rules

- Validate the Boolean setting label and last-modified timestamp without storing URL values.
- Group 1 requires available Primary and Failover non-contact.

- Missing, null, malformed, wrong-type, and warm-instance refresh behavior remain open.
- Delayed/repeated processing must not duplicate business outcomes.

## API / Backend Impact

- Shared `InsService` and `InsSmsService` routing changes for 15 requests.
- Route selection occurs before request execution; the old try/catch fallback is removed.
- Existing payloads, responses, authentication, authorization, and handlers are otherwise unchanged by confirmed scope.
- Sanitized calling-Lambda and receiving-service evidence is required.

## Integration Impact

- Mutually exclusive Primary/Failover destinations.
- Twilio, reports, alarms, Mobile authentication, nursing follow-up, and outbound SMS are affected.
- Failure must not deliver providers' messages, resolve alarms, deliver reports, create sessions, reassign groups, change billing, or create follow-ups.

## Permissions / Roles

## Regression Risk

- Critical safety risk for missed, delayed, duplicate, or falsely resolved alarms and Welfare Checks.
- High operational risk if shared routing selects the wrong backend during normal service or disaster recovery.
- High data-integrity risk for billing, reassignment, reports, sessions, follow-ups, and alarms.
- High notification risk for missed/duplicate SMS and alarm messages.
- High compatibility risk because 15 requests across multiple platforms share routing.
- Medium support risk without sanitized routing correlation.

## Confirmed Decisions

- DEC-013: `INSFailover` defaults to `false`; `false` selects only Primary and `true` selects only Failover for all 15 requests, with no automatic fallback.
