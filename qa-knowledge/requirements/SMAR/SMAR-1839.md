## Requirement Summary

SMAR-1839 internally refactors the Stock and Stock Transaction APIs into the vertical-slice architecture. Existing externally observable behavior must remain unchanged. Regression covers the documented APIs, CP Desktop Asset Management → Stock Levels and Transaction History, and Service Request workflows that allocate, dispatch, reverse, or display stock movements.

## Confirmed Scope

- CP Desktop Asset Management → Stock Levels.
- Manual Stock actions and Transaction History.
- Stock API v2 GET, POST, and threshold PATCH.
- StockTrans API v2 GET and POST.
- Service Request stock allocation, quantity edits, dispatch, cancellation/closure reversal, and observable non-replay.
- Stock, StockTrans, and Service Request record isolation and persistence evidence.

## Out of Scope

- New product behavior, schema, enum representation, validation message, notification rule, job/queue contract, or idempotency guarantee introduced only for this refactor.
- Mobile SOS, Mobile Carer, Portal Web, CP Web, billing, QuickBooks, reports, and exports unless a supplied case proves a direct existing Stock consumer.
- Production mutation testing. Use isolated non-production records.
- Exact internal repository, table, handler, queue, or log names not supplied by approved technical evidence.

## Business Rules

1. Total/Qty equals In Stock plus Pending Return.
2. Available equals Total minus Allocated.
3. On Order is stored independently and does not contribute to Total or Available.
4. Creating Stock accepts zero, null, or omitted operational quantities according to the Stock API and calculates Qty/Available as read-only values.
5. A Stock transaction belongs to one StockUuid and must not mutate another Stock record.
6. Transaction quantity validation follows the documented type rules: standard types require greater than zero, Adjustment is non-zero, and Stocktake is zero or greater.
7. Undefined transaction and Service Request effects are compared with recorded pre-refactor behavior under D1–D3 rather than invented.

## UI/UX Rules

- CP Desktop Stock Levels displays persisted quantities and calculated Total/Available for the selected Stock record.
- Transaction History is scoped to the selected Stock and supports the confirmed filters and pagination inputs.
- Refresh/reopen shows the final persisted state without creating a transaction.
- Exact incompatible-filter behavior and stable ordering remain QA Assumptions until pre-refactor evidence is recorded.

## Validation Rules

- Invalid Stock or StockTrans input produces no partial Stock, StockTrans, Service Request, or audit-like update.
- Follow-up GET evidence must distinguish accepted records from rejected requests.
- Negative Available values remain visible when Allocated exceeds Total.
- Read-only Qty and Available values cannot be supplied as authoritative persisted calculations.
- Exact error schemas, duplicate-POST responses, and authorization failures remain Open Questions unless observed.

## API / Backend Impact

The public regression boundary is `/lg/stock/v2` and `/lg/stocktrans/v2` as documented. Primary evidence is the HTTP response, follow-up GET, CP refresh/reopen, final Stock bucket values, StockTrans count, reference, timestamp, method, type, effect, and StockUuid. Internal vertical-slice handler/repository structure is developer-only implementation evidence and is not an independent product expectation.

## Integration Impact

- CP Desktop consumes Stock and StockTrans state.
- Service Requests can create or reverse existing Stock allocations and dispatch movements; exact outcomes must match recorded pre-refactor behavior.
- No new notification, billing, report, export, alert, device, job, or queue behavior is confirmed.

## Permissions / Roles

Use an authorized non-production tester able to view Stock Levels, run applicable Stock actions, process isolated Service Requests, and call the documented APIs. Exact authentication mechanism, unauthorized response, role matrix, and cross-tenant access contract are Open Questions and require approved security evidence before executable expectations are added.

## Background Jobs / Queues

No job or queue contract is confirmed. Duplicate/retry processing is covered through observable final-state and transaction-count evidence; internal exactly-once behavior requires developer-supported correlation evidence.

## Audit / History / Logs

Use tester-visible creator/updater fields, timestamps, StockTrans history, references, and counts. When duplicate or delayed processing cannot be distinguished through APIs and CP, obtain developer-supported privacy-safe correlation/log evidence. Do not store credentials or production identifiers.

## Reports / Export Impact

None confirmed.

## Cross-Platform Sync Impact

CP Desktop and the documented APIs must converge on the same final Stock and StockTrans state after refresh. No other platform is confirmed.

## Privacy / Sensitive Data Impact

Use synthetic non-production Stock, Service Request, user, client-file, and device data. Redact client identity, health/contact information, authentication material, tenant secrets, and unrelated identifiers from screenshots and logs.

## Test Data, Isolation, and Cleanup

- Capture Stock and StockTrans baselines before every mutation.
- Use unique privacy-safe references and isolated Stock/Service Request records.
- Restore only the records changed by the case after evidence capture.
- Preserve required audit/history and do not delete shared or historical records.
- Use Developer-supported reset where Stock definitions cannot be safely removed.

## Required Test Instrumentation

- Tester-accessible: CP Stock Levels, Transaction History, Service Request state, API request/response, follow-up GET, record counts, quantities, references, and timestamps.
- Developer-supported: exact persistence, correlation, retry, partial-write, or internal authorization evidence when public behavior cannot distinguish the outcome.
- Operations-supported: environment reset only when isolated test records cannot be restored safely.

## Regression Risk

- Incorrect Stock calculations or cross-record mutation.
- Missing, duplicated, or partially applied StockTrans movements.
- Stale CP values after a successful API or Service Request action.
- Incorrect Service Request allocation, dispatch, reversal, or peripheral quantity.
- Validation regressions that partially persist data.
- API consumer incompatibility after response, enum, path, or error-contract changes.

## Confirmed Decisions

- D2 / DEC-021: Return Received preserves the pre-refactor result; exact bucket values remain open until recorded.
- D3 / DEC-021: Pre-refactor CP/API behavior defines Service Request stock outcomes and transaction details; exact values remain open until recorded.
