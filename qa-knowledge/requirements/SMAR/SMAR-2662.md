## Requirement Summary

LifeGuardServices must cryptographically validate every affected JWT against trusted signing configuration before using identity, user, role, tenant, token-purpose, or other protected claims. Unsigned, tampered, corrupted, unsupported-algorithm, or untrusted-key tokens must not create an authenticated context or reach protected business processing. The fix applies to the shared OAuth and NoAuth claim-reading paths identified by SMAR-2662 while preserving existing valid signed-token workflows.

## Confirmed Scope

- Shared JWT handling in LifeGuardServices `Configurer.cs` and `OAuthService.cs`.
- Authentication — OAuth paths triggered by protected OAuth APIs.
- Authentication — NoAuth claim-reading paths identified by the ticket.
- `PUT /user/v2`.
- Authenticated `PUT /user/v2/auth/password`.
- Query-string-token `PUT /user/v2/auth/password`.
- `POST /user/v2/auth/token`.
- `GET /billing/v2/device/{Uuid}`.
- `PATCH /billing/v2/device/{Uuid}`.
- `GET /billing/v2/group/{Uuid}/codes/{Code}`.
- `DELETE /billing/v2/group/{Uuid}/codes/{Code}`.
- CP Desktop, CP Web, and Portal Web login or password regression where the approved cases explicitly identify those applications.

## Out of Scope

- Redesigning authorization, roles, tenant permissions, password policy, account-state handling, lockout, or rate limiting.
- Changing existing endpoint request or accepted response schemas beyond JWT validation.
- Storing or exposing production JWTs, private keys, signing secrets, credentials, or client data in QA evidence.
- General penetration testing beyond the approved JWT and consumer regression groups.

## Business Rules

1. Claims cannot establish identity or authorization until cryptographic signature validation passes.
2. A token that is structurally readable but unsigned is not authenticated.
3. Signature validation uses trusted configured signing material and an explicitly approved algorithm.
4. Rejected authentication creates no user, password, device, billing, group-code, or cancellation mutation.
5. Existing authorization and business validation still execute after valid authentication; valid authentication does not bypass them.
6. Existing valid, compliant, unexpired tokens using retained trusted configuration remain compatible.

## UI/UX Rules

- CP Desktop, CP Web, and Portal Web retain their existing login, session, and password-reset flows when a valid signed token is issued and accepted.
- Invalid-token failures use the existing sanitized application recovery flow; exact messages require runtime confirmation.

## Validation Rules

- Reject unsigned tokens and `alg: none`.
- Reject missing, corrupted, or tampered signatures.
- Reject payload or header modification after signing.
- Reject tokens signed with an untrusted key.
- Reject non-allowlisted algorithms and algorithm/key-type substitution.
- Reject unsafe unknown or attacker-controlled `kid` selection where `kid` is supported.
- Reject malformed, truncated, extra-segment, invalid-encoding, and oversized token forms through a controlled authentication error rather than an uncontrolled server error.
- Enforce applicable issuer, audience, lifecycle, and token-purpose rules after signature validation according to deployed configuration.

## API / Backend Impact

The change affects shared LifeGuardServices token parsing and validation before handler processing. API evidence must distinguish authentication rejection from business validation and must prove no protected handler mutation occurred for invalid tokens. Exact accepted status codes remain endpoint-specific and require deployed contract evidence.

## Integration Impact

- OAuth consumers must continue accepting valid signed tokens.
- NoAuth billing consumers identified by Jira must apply the corrected validation without changing their existing device or group-code workflows.
- Login issuance must produce a signed token compatible with affected CP and Portal consumers.
- Forgot-password tokens must remain limited to their intended reset flow.

## Permissions / Roles

Existing authorization, role, tenant, and resource-scope rules are unchanged. Invalid or forged claims cannot grant identity, role, tenant, or cross-user access. Valid authentication must not authorize an otherwise prohibited action.

## Background Jobs / Queues

No new job or queue behaviour is confirmed. Rejected authentication must not start downstream work that normally depends on an accepted user, password, device, billing, group-code, or cancellation action.

## Audit / History / Logs

- Record a sanitized authentication outcome and correlation identifier when existing policy supports it.
- Do not log complete JWTs, signing keys, credentials, decoded sensitive claims, or unnecessary client data.
- Rejected requests may create a security event but do not create an accepted business-action audit entry.
- Exact log category, field names, retention, and instrumentation ownership remain open.

## Reports / Export Impact

None confirmed.

## Cross-Platform Sync Impact

Valid signed-token login and password workflows must remain usable from CP Desktop, CP Web, and Portal Web where covered. Rejected forged tokens must not create a state that later appears on another application.

## Privacy / Sensitive Data Impact

Use synthetic non-production users, devices, groups, and codes. Redact complete tokens, credentials, signing material, query tokens, personal data, tenant identifiers, and unnecessary claims from screenshots, logs, exports, and stored evidence.

## Test Data, Isolation, and Cleanup

- Use isolated active QA users with reversible profile and password changes.
- Use disposable QA device and group-code records for mutation and deletion coverage.
- Use controlled non-production signing material only; production signing material is prohibited.
- Preserve required sanitized security and audit evidence.
- Roll back reversible user/password changes and remove only disposable records created for this suite.

## Required Test Instrumentation

- Deployed algorithm allowlist, trusted key selection, and `kid` behaviour.
- Correlated authentication decision and protected-handler entry or non-entry evidence.
- User, password, device, and group-code persistence read-back.
- Existing audit/security log output without sensitive token or key material.
- Endpoint-specific accepted and rejected HTTP contracts.
- Development- or operations-supported evidence is required where these are not tester-accessible.

## Regression Risk

Shared JWT validation can affect every OAuth consumer and the listed NoAuth/login/reset consumers. Overly permissive validation leaves an authentication bypass; overly restrictive validation can block CP, Portal, password, billing-cancellation, device, and group-code workflows. Reusable regression is recorded in the regression map.

## Confirmed Decisions

- DEC-014 — Affected LifeGuardServices consumers validate JWT signatures against trusted configuration before claims are trusted; unsigned or untrusted tokens cannot authenticate.
