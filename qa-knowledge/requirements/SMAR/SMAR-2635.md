## Requirement Summary

The Portal Account Cancellation workflow must stop sending the legacy HMAC hash and old API key directly to the old backend. The Portal instead sends its existing NoAuth authentication context to one of two AWS endpoints. AWS validates the caller context and proxies the business request through `InsService`, which uses the new backend-only HMAC mechanism covered by SMAR-2657.

When the client has no other active file or device services, Portal calls `PATCH /lg/file/v2/{Uuid}` to suspend the client file. When other active services exist, Portal calls `POST /lg/file/v2/{Uuid}/statusrequest` to request suspension without immediately suspending the file. Both successful responses have an empty body. Existing Account Cancellation content, billing sequencing, and user interaction remain unchanged except for the underlying request route and authentication ownership.

## Confirmed Scope

- Portal Web Account Cancellation for an authenticated NoAuth session.
- `PATCH /lg/file/v2/{Uuid}` with `Status` and `Reason`.
- `POST /lg/file/v2/{Uuid}/statusrequest` with `Status`, `Name`, `GrpName`, and `Reason`.
- `Status` is limited to `Suspended` for this ticket.
- AWS-to-old-backend proxying through `InsService` and the SMAR-2657 backend HMAC dependency.
- Removal of `oldApiSecret` and `oldApiXApiKey` from Portal environment configuration and session models.
- Removal of the associated Portal pipeline-variable setup.
- Removal of Portal-side legacy HMAC and direct-dispatcher logic for the two actions.
- Preservation of existing Account Cancellation UI and business outcomes.

## Out of Scope

- General penetration testing.
- Full browser-storage, source-map, CORS, cache, or service-worker security review.
- Backend `InsService` secret-management testing owned by SMAR-2657.
- Full Account Cancellation billing regression beyond the scenarios required to reach the two migrated routes.
- Changing unrelated Portal or CP Web requests that use OAuth or other authentication.
- Mobile application, CP Desktop, CP Web, alarm, FCM, SMS, Twilio, QuickBooks, report, or export behaviour.

## Business Rules

1. A client file with no other active file/device services uses the direct-suspension PATCH route.
2. A client file with other active services uses the suspension-request POST route.
3. A direct-suspension outcome sets the target file to Suspended and schedules its deletion for 30 days after suspension.
4. A suspension request does not immediately suspend the file, alter other active services, or create a deletion schedule.
5. A suspension request initiates the established configured enquiries workflow.
6. An already Suspended file displays the existing already-deleted state and does not invoke either migrated endpoint.
7. Existing Village, LinkingCode, IAB, and no-billing Account Cancellation sequencing remains unchanged.
8. Portal displays completion only after the selected AWS request is accepted and must not fall back to the old dispatcher after an AWS failure.

## UI/UX Rules

- Existing Account Cancellation authentication, wording, warnings, controls, confirmation, loading state, and final navigation remain unchanged for the applicable scenario.
- The migration introduces no user-entered legacy authentication field or additional user step.
- Delete Account must not be submitted repeatedly while a request is pending.
- An AWS failure must not display a completed suspension or completed suspension-request state.
- The exact generic failure message and retry presentation remain implementation-dependent unless a case cites a specific approved message.

## Validation Rules

Confirmed:

- PATCH accepts the target client-file UUID in the path and sends `Status` and `Reason`.
- POST accepts the target client-file UUID in the path and sends `Status`, `Name`, `GrpName`, and `Reason`.
- `Suspended` is the only supported Status for this ticket.
- A successful response body is empty.

QA Assumptions retained from the approved suite:

- Missing, malformed, expired, tampered, or wrong-purpose NoAuth values are rejected before `InsService` is called.
- A token cannot address a different client-file UUID.
- Required, malformed, null, blank, whitespace-only, wrong-type, and unsupported body values are rejected before legacy processing.
- Status input is case-insensitive and normalized to `Suspended`.
- Caller-supplied legacy identifiers, time, SubmittedBy, hash, API key, and device UUID cannot override trusted mapping.
- Duplicate or already-processed requests produce a deterministic conflict or idempotent response without duplicate effects.

## API / Backend Impact

- Portal invokes the two new AWS endpoints using the existing NoAuth authentication context.
- AWS owns NoAuth validation, client-file authorization, request validation, and mapping to the legacy request contract.
- AWS generates backend-owned metadata and invokes the old backend through `InsService`.
- Portal must not calculate a HMAC hash, attach the old API key, attach the downstream device UUID, or invoke `/api/dispatcher` for these actions.
- SMAR-2657 must supply the backend-only HMAC mechanism before successful end-to-end integration can be verified.
- Exact routes, handlers, functions, persistence objects, and generated infrastructure could not be verified in the available repository.

## Integration Impact

- PATCH maps to `SuspendClientFileRequest`, resulting in one Suspended file and one 30-day deletion lifecycle.
- POST maps to `RequestClientFileSuspensionRequest`, resulting in one configured enquiries workflow while the file and other active services remain unchanged.
- Relevant IAB cancellation must complete before the direct-suspension PATCH when the existing workflow requires that sequence.
- Failed requests must not create a false file status, deletion schedule, suspension request, billing change, or enquiries action.
- Legacy response details, authentication values, internal hosts, and stack traces must not be exposed to Portal.

## Permissions / Roles

- The workflow starts from an authenticated Account Cancellation NoAuth context rather than a CP/Portal employee role.
- Exact token purpose, lifetime, file/device claims, and authorization-failure contract remain Open Questions pending implementation evidence.

## Background Jobs / Queues

- Direct suspension schedules the established 30-day deletion lifecycle.
- Suspension request uses the established enquiries workflow, which may include an email job or queue.
- Exact job names, queue names, retry limits, deduplication keys, and lost-response reconciliation are Open Questions.

## Audit / History / Logs

- Failures and retries require sanitized correlation evidence when the primary downstream behaviour cannot otherwise be observed.
- Logs must not expose NoAuth values, HMAC values, API keys, unnecessary client information, internal hosts, or raw legacy payloads.
- Exact audit/activity entries and whether duplicate attempts create separate technical records remain Open Questions.

## Reports / Export Impact

None.

## Cross-Platform Sync Impact

No cross-platform UI change is confirmed. Client-file status and deletion lifecycle remain shared backend data and must not be falsely changed by a failed or misrouted request.

## Privacy / Sensitive Data Impact

- Use isolated non-production client files, mobile numbers, verification destinations, and enquiries recipients.
- Mask tokens, client identifiers, contact information, and legacy authentication data in screenshots, logs, errors, and test evidence.
- A wrong-file authorization failure must not disclose the other client file’s name, group, services, contact information, or identifiers.

## Test Data, Isolation, and Cleanup

- Use resettable non-production files for Active, Suspended, other-active-service, IAB, Village/LinkingCode, and no-billing states.
- Route verification codes and suspension-request emails only to approved QA recipients.
- Record initial file status, billing state, deletion schedules, pending requests, and email evidence before execution.
- Cancel or safely complete test deletion schedules after evidence collection without deleting unrelated data or required audit evidence.
- Do not reuse a destructive test file across parallel or duplicate-request cases unless it is reset to the documented initial state.

## Required Test Instrumentation

- AWS request/response evidence that masks NoAuth and internal credentials.
- Correlated `InsService`/legacy request evidence for mapping checks.

## Regression Risk

Account Cancellation regression covers NoAuth login, existing UI and billing sequencing, direct suspension, suspension request, already-Suspended handling, correct client-file targeting, failure handling, duplicate prevention, removal of Portal legacy credentials, and the absence of direct dispatcher fallback.
