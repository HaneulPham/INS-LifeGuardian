## Requirement Summary

The SmartHome Legacy Backend must accept OAuth authentication only for eighteen current Jira request classes. A valid HMAC-only call to one of those classes must be rejected before protected data is returned or write processing starts. Three multi-consumer requests remain accessible through either independently valid OAuth or independently valid HMAC authentication: `FindDevicesPortalRequest`, `FindFilesPortalRequest`, and `GetClientFileRequest`.

Accepted OAuth requests retain existing authorization, validation, response data, and business outcomes. Rejected requests use the established Old Backend sanitized authentication-failure contract and create no partial write, accepted-action audit entry, relationship change, workflow, or applicable downstream action.

## Out of Scope

- Removing HMAC from the three exception request classes.
- Changing OAuth issuance, claims, roles, tenant permissions, or token expiry rules.
- Changing business validation or response data after authentication succeeds.
- A standalone Group 4 authorization and tenant-isolation suite; existing authorization regression remains applicable.
- CP Desktop, CP Web, and cross-platform detailed Group 6 cases removed by the approved v28 scope.
- Executable mixed-credential expectations before BA/Product/Development confirms precedence.
- General penetration testing or a platform-wide authentication redesign.

## Business Rules

1. Each OAuth-only class rejects a request that lacks valid OAuth even when valid legacy HMAC is supplied.
2. Valid OAuth continues through existing authorization, tenant, validation, and business rules.
3. Each exception remains independently accessible using valid OAuth-only or valid HMAC-only authentication.
4. Authentication rejection precedes protected reads and write business logic.
5. A rejected write creates no partial record, relationship change, state transition, accepted-action audit entry, or applicable downstream action.
6. Authentication responses do not disclose credential validity, tenant existence, or protected resource details.
7. Mixed valid/invalid credential precedence remains unresolved and is not executable.

## UI/UX Rules

- Portal Web workflows retain existing navigation, controls, validation, loading, permissions, and completion behaviour.
- Portal must use OAuth and must not retry a rejected OAuth request through HMAC.
- Expired or invalid OAuth follows the existing sanitized session/login recovery flow without protected data or false completion.

## Validation Rules

Confirmed:

- The eighteen current classes require valid OAuth.
- HMAC-only calls to those classes are rejected.
- Three exceptions retain valid OAuth-only and valid HMAC-only paths.
- Existing authorization and request validation continue after authentication.

Open:

- Exact numeric authentication-rejection status and payload fields.
- Mixed valid/invalid credential precedence for exception routes.
- Exact handling of malformed extra credential headers when another credential is valid.

## API / Backend Impact

- Authentication selection is expected to be enforced centrally in or before `DispatchController`, based on the Jira developer note.
- Request classification must match the current eighteen-class matrix and three exceptions.
- Existing handlers and response schemas remain unchanged after authentication succeeds.
- `{{domain}}/api/dispatcher` and `POST` in the approved suite remain execution placeholders until current routing is verified.

## Integration Impact

- AWS integrations continue using HMAC for the three exceptions under SMAR-2657.
- Existing device consumers continue using the supported HMAC path for `GetClientFileRequest` under the SMAR-2637 dependency.
- Rejected Community News, group, procedure, concierge, and address-change writes must not initiate their established downstream processing.
- Exact event, job, queue, cache, and provider names require implementation evidence.

## Permissions / Roles

- OAuth success does not bypass existing role, tenant, group, client-file, or resource authorization.
- Portal test users require only the permissions needed for the selected workflow.
- Authentication and authorization failures must not expose protected resource existence or data.

## Background Jobs / Queues

- No new job or queue is introduced by this ticket.
- Rejected writes must not enqueue their applicable established workflow.
- Exact job and queue names could not be verified.

## Audit / History / Logs

- Rejected authentication may create a sanitized security log under existing policy but not a successful business-action audit entry.
- Correlation evidence must show the authentication decision and absence of protected processing when the outcome is otherwise unobservable.
- Tokens, HMAC material, internal hosts, tenant identifiers, and unnecessary client data must be masked.

- Use independent records for accepted and rejected write variants.

## Regression Risk

- High security risk if an OAuth-only class still accepts HMAC-only authentication.
- High compatibility risk if any exception is accidentally made OAuth-only.
- High data-integrity risk if rejected writes reach persistence or downstream workflows.
- Medium Portal risk if existing OAuth calls, session recovery, permissions, filtering, or response parsing change.
- Medium privacy risk if rejection responses expose credential or protected-resource details.

## Confirmed Decisions

- DEC-006: Use the existing Old Backend response contract; do not hardcode `401 Unauthorized` without implementation evidence.
- DEC-010: The approved v28 detailed client regression scope is Portal Web only. This supersedes DEC-005 and removes the previous CP Desktop/cross-platform Group 6 cases.
