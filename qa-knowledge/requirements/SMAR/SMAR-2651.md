## Requirement Summary

CP Desktop must make **Billing** available for manual Service Request creation while enforcing Billing-specific lifecycle rules. Only Technical Issue requests can be converted to Billing; Billing requests cannot be converted to another Type. Billing requests do not use the Progress/Setup Checklist UI and can use the normal Service Request status workflow except Dispatch.

The Jira summary initially says users can change a request “to or from” Billing, but the detailed Expected Behaviour explicitly states that Billing cannot be changed to another Type. The detailed rule is also reflected in the approved Group 2 cases and is therefore the stored expectation.

## Confirmed Scope

- CP Desktop → Client File Detail → Service Requests.
- Manual Billing Service Request creation, required-field validation, Items, cancel, save, reopen, and duplicate prevention.
- Community Centre-generated Billing request regression from SMAR-2157.
- Technical Issue → Billing conversion.
- Billing Type locking for manual and automatically generated requests.
- New Install and Repair Devices conversion restrictions.
- Billing Progress-tab and Setup Checklist suppression.
- Billing status transitions and Dispatch exclusion.
- Persistence after request and Client File reopen.

## Out of Scope

- Changing the Community Centre generation rules or generated field values defined by SMAR-2157.
- New Billing calculations, invoices, QuickBooks behavior, reports, exports, notifications, or alerts; no such change is specified by SMAR-2651.
- Mobile SOS, Mobile Carer, Portal Web, CP Web, and CP Desktop areas outside Client File Service Requests.
- Exact API routes, database documents, audit schemas, or backend validation mechanisms not identified by the approved evidence.

## Business Rules

1. The create Type dropdown contains Technical Issue, New Install, Repair Devices, and Billing; Billing appears once and can be selected.
2. A manually created Billing request is associated with the selected Client File and retains its submitted fields and Items after reopen.
3. Cancelling Billing creation or conversion stores no draft change or partial Item relationship.
4. Only an existing Technical Issue request in an editable, non-Dispatch state can be converted to Billing.
5. New Install and Repair Devices cannot be converted to Billing.
6. A Billing request cannot be changed to another Type, whether manually created or automatically generated.
7. Billing does not expose the Progress/In Progress checklist tab, checklist steps, completion controls, percentages, or checklist status.
8. Billing can move through supported normal Service Request statuses except Dispatch.
9. Type remains Billing after each permitted status change.
10. A request cannot persist the combination Type = Billing and Status = Dispatch.

## UI/UX Rules

- Billing is visible once in the creation Type dropdown.
- For an existing Billing request, the Type dropdown remains enabled but offers only Billing.
- Billing is absent when editing New Install or Repair Devices.
- Dispatch is absent from the Billing Status dropdown.
- When Billing is selected while Dispatch is already selected, the UI must either make Billing unavailable or remove Dispatch and require a valid status.
- The Progress/In Progress checklist tab is hidden for Billing in In Progress.

## Validation Rules

- Existing required-field validation applies to Billing creation and prevents persistence until required values are supplied.
- Adding multiple Items preserves each distinct selection; removing an Item before save persists only the remaining Items.
- Cancel prevents creation, Type conversion, non-Type edits, and Item relationships from being stored.
- Converting Technical Issue updates the existing request identifier instead of creating a new request.
- Invalid Type/status combinations produce no false save, partial Type/status update, or duplicate request.

## API / Backend Impact

The approved UI cases require create, update, Item association, status, and persistence behavior to be reflected when the same Service Request is reopened. Exact endpoints, methods, request/response schemas, server-side enum enforcement, and idempotency contracts remain Open Questions.

## Integration Impact

- The existing SMAR-2157 Community Centre workflow must continue generating a Billing Service Request for the correct Client File.
- No new billing export, QuickBooks, notification, alert, SMS, email, FCM, Twilio, or queue behavior is confirmed for SMAR-2651.

- Remove disposable requests and Item relationships after execution when permitted; retain required audit evidence.
- Do not change shared Community Centre records without a rollback plan.
